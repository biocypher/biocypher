\subsection{Case study 3: OmniPath Protein–Pathway Extension}
\label{sup-sec:omnipath-pathways}
%To compare the ease of extensibility for the two adapters, we now add in another data source\cite{edwin_carreno_2026_20742395}.

    This case study evaluates the extensibility of the two adapter approaches by incorporating an additional dataset containing protein-pathway associations~\cite{Carreno2026_synthetic_proteinpathway}.

\subsubsection{Knowledgraph Graph model}

    The knowledge graph model from Case Study~1 is extended with the node type \textit{pathway} and the relationship \textit{participates in}, which links proteins to the biological pathways in which they are involved. Figure~\ref{fig:case2-kg-model} illustrates the extended model.

\subsubsection{Adapter implementations}
    Two additional adapters were developed to build the extended knowledge graph.

    \begin{itemize}
        \item \textit{Python code adapter extended (C):} The Python implementation uses separate adapter modules for each source dataset. Each module transforms its corresponding records into the node and edge tuples required by BioCypher. The tuples generated from the protein-protein interactions and protein-pathway datasets are then passed to BioCypher to construct the combined knowledge graph. The implementation is available in the \href{https://github.com/iulusoy/python-ui-adapter-extended}{Python adapter extended repository}.

        \item \textit{OntoWeaver low-code adapter extended (D):}
        The OntoWeaver implementation defines a separate declarative mapping for each source dataset. OntoWeaver applies its built-in reconciliation mechanisms while combining entities and relationships from the two sources before passing the resulting representation to BioCypher. Data-quality issues that cannot be handled by the built-in mechanisms, such as structurally malformed records, require custom transformation logic that extends the Ontoweaver's capabilities. The implementation is available at \href{https://github.com/ecarrenolozano/ontoweaver-adapter-extended}{Ontoweaver adapter extended repository}.
    \end{itemize}

\subsubsection{Implementation comparison}

    Table~\ref{tab:comparison-case2} compares the two extended adapters. The plain Python adapter requires additional code for data transformation and reconciliation, by default BioCypher does not reconciliate data. One example of this behavior can be found when two identic entities have different properties: BioCypher will save the first set of properties encountered instead of reconciliate them. On the other hand, OntoWeaver uses an additional mapping file and built-in reconciliation mechanisms. However, malformed records and source-specific inconsistencies may still require custom transformers.
